# apar.md — AP / AR Tracker (`apar.html`)

> Read this together with the root `CLAUDE.md`. Deep-dive for the AP / AR Tracker only.
> App accent: **green** `--accent:#1f4d38` (AR green `#2f8f6b`, AP red `#a8443a`). ~4,400 lines.

## What it does

Accounts payable and receivable: bills and invoices, vendor/customer parties, pay runs, aging, deposits, recurring items, a cash view, and a calendar. Reads orders for context.

## Data & storage

- **Owns RTDB:** `apar/*` —
  - `apar/entries` (the core bills/invoices), `apar/accounts`, `apar/vendorAccounts`, `apar/vendorAliases` + `apar/vendorAliasNames`, `apar/vendorPriority`, `apar/userNames`
  - `apar/recurring`, `apar/audit` (audit trail), `apar/depositLog`, `apar/depositBuckets`, `apar/apSplit`, `apar/customerDelay`
- **Reads:** `orders`.
- **localStorage:** `apar_autobackup`, `apar_last_backup`, `bsmp_apar_brief`, `bsmp_sidebar_pinned`.
- **Write helpers:** `dbSet` / `dbUpdate` / `dbRemove`. Writes are tracked (`trackWrite`, `queueFailure`, `retryFailedWrites`, `writeOverlay`) so a failed save is retried and surfaced — keep that resilience when refactoring saves.
- **Daily auto-backup/restore:** `maybeAutoBackup` / `maybeAutoBackupOnce`, `buildBackup` / `buildAparSnapshot`, `downloadBackup`.

## Core areas (where to work)

- **Entries (bills/invoices):** `entryCard` / `entryRow` / `entryHistoryHtml`, `rowTotal`, `statusOf`, `sortEntries` / `sortBills` / `sortListBy`. `allEntries` / `allEntriesRaw` are the main accessors; `deriveAP` / `deriveAR` split them.
- **Parties & dedup:** `canonicalParty`, `custKey` / `vendorKey` / `emailKey`, `buildSpellingMap`, alias handling (`_aliasVariantLabel`). This deduplicates the same vendor/customer typed different ways — be careful, since it affects grouping and totals.
- **Auto-combine:** bills with the same vendor + PO are auto-combined. Look here first if bill grouping changes.
- **Pay run:** `renderPayRun`, `payrunBillMatchesFilter`, `payrunFilterActive`, `planAccount`, `fillAccountSelect`.
- **Aging:** `agingTable`, `bucketize` / `bucketList`, filter chips.
- **Recurring:** `generateRecurring`, `autoGenerateDue`, `advanceDue`, `showRecurEditor`, `recurMethodNote`, semimonthly logic (`firstSemimonthly`), `adjustToWorkday`.
- **Deposits:** `depositLogHtml`, `seedDepositBuckets`, deposit buckets.
- **Balance math:** `evalMath` is a **safe arithmetic evaluator** for balance inputs (so users can type `1200+50`); `parseDiscount` / `discountActive`. Don't replace `evalMath` with `eval()`.
- **Import review:** `renderImportReview`, `imp*` helpers (`impAmount`, `impDate`, `impSplitLine`, `impStatus`, `impHeaderField`) parse pasted/imported invoice data.
- **AI:** `aparNarrate`, `updateAiStatus`, `aparFmtBrief`.
- **AI Extract (sidebar):** `aiHandle` sends the PDF/photo to the `bsmp-ai-extract` worker and always gets back a JSON *array* of invoices. One or two → the old one-at-a-time form (`fillPreview` / `aiAdd`). **Three or more → statement mode** (`aiStmtShow` → `aiStmtMatch` → `renderAiStmt` → `aiStmtCommit`): a vendor statement of account becomes one bill per line, reviewed in a table. Every line is matched against `allEntries()` first (`aiFindExisting`: invoice # → PO # → same amount with no ref; refs compared through `aiRefKey`, vendors through `aiSameVendor` prefix match) and lands as **add** (new manual bill), **fill** (an existing PO-pipeline bill gets the statement's amount / invoice # / date via `ovlPatch`) or **have** (already entered, skipped). A PO bill can be claimed by only one statement line — vendors like McMaster ship one PO as several invoices, so the extra invoices become their own bills. Harness: `dev/build_apar_stmt_test.py` (McMaster statement fixture).
- **Audit trail:** `logAudit`, `auditRowHtml`, `auditSorted` — this feeds the Activity page and is the closest thing to the immutable trail AS9100 would want. Preserve append-only behavior.

## Entry record (rough shape)

Common fields: `party`, `type` (AP vs AR), `amount`, `account`, `status`, `date`, `dueDate`, `po`, `balance`. Type drives whether it's derived into AP or AR.

## Gotchas

- **Party canonicalization is load-bearing.** A change to `canonicalParty` / alias maps can silently merge or split parties and shift AP/AR totals. Test totals after touching it.
- Writes are queued/retried; if you bypass `dbSet`/`dbUpdate` you lose the failure-retry + audit behavior.
- `evalMath` must stay a *safe* evaluator — no `eval`, no `Function` on user input.
